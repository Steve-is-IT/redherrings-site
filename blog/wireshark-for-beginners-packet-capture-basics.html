Wireshark for beginners: packet capture basics

A packet capture is a few thousand small events in time order, and Wireshark's job is to let you look at them from the right distance: the whole conversation table, one stream, or one packet's bytes. This is the first hour: the handful of views and filters that get a beginner from an opened pcap to a readable story.

Open the capture and fix the clock

Wireshark is free; install it from wireshark.org (our tools page has a setup note). Open the .pcap or .pcapng with File, then Open. You will see three panes: the packet list on top, the decoded fields of the selected packet in the middle, and the raw bytes at the bottom. Beginners live in the top pane. Analysts spend more time in the middle one.

Before anything else, set the time display. View, then Time Display Format, then UTC Date and Time of Day. The default shows seconds since the start of the capture, which is useless for lining packets up against a log file, and the local-time option silently uses whatever zone your laptop is in. Pick UTC and say so in your notes.

Display filter vs capture filter

Wireshark has two filter languages, and confusing them is the most common beginner error.

  • A capture filter decides what gets recorded in the first place. It uses BPF syntax (port 53, host 10.0.0.5) and is set before you start capturing. If you are opening a file someone else captured, it is irrelevant: the decision has already been made.
  • A display filter decides what you see out of what was recorded. It uses Wireshark's own syntax (dns, ip.addr == 10.0.0.5, http.request) and goes in the green bar above the packet list. Nothing is deleted; clear the bar and everything is back.

In the classroom you almost always have a file, so you are always writing display filters. The ones you will type most:

  • ip.addr == 10.0.0.5: anything to or from a host.
  • dns, http, tls, smb2, ftp: one protocol.
  • tcp.port == 4444: one port, either direction.
  • tcp.stream eq 12: one TCP connection, start to finish.
  • !(arp or dhcp): hide the chatter.

The bar turns red when the syntax is wrong and green when it is valid. You can also right-click any field in the middle pane and choose Apply as Filter, which writes the syntax for you and is how most people learn it.

Statistics: Conversations and Endpoints

Do not start by scrolling packets. Start with Statistics, then Conversations. The IPv4 and TCP tabs list every pair of hosts that talked, with packet counts, bytes in each direction, start time and duration. Sort by bytes to see where the volume went. Sort by duration to see what stayed connected. Sort by start time to see the order things happened. A capture with 40,000 packets usually has a dozen conversations that matter, and this table is where you find them.

Endpoints is the same data by single host rather than by pair: which addresses appear at all, and how much each sent and received. It is the quickest answer to "which internal host is this capture about" and "how many outside addresses did it talk to". Protocol Hierarchy, in the same menu, tells you what kinds of traffic are present before you filter for any of them.

Right-click any row in Conversations and choose Apply as Filter to drop straight from the table to the packets behind it.

Read a capture from the outside in: who talked to whom, then which conversation, then which stream, then which packet. Starting at the packet is starting in the wrong place.

Follow the stream, export the objects, save the subset

Once you have a conversation, select one of its packets and choose Analyze, then Follow, then TCP Stream. Wireshark reassembles the whole connection and shows it as text, one color per direction. For a plaintext protocol this is the moment the traffic becomes legible: an HTTP request and its response, an FTP login and the file it fetched, an SMTP envelope. Use the direction dropdown to show one side only, and Save As to keep the stream as a file.

File, then Export Objects, then HTTP (or SMB, FTP-DATA, TFTP) lists every file that crossed the wire in that protocol and lets you save them. Hash what you save; the hash is the thing you will report. This is how a student in First Look: Reading a Packet Capture gets from "a file transfer happened" to "this file, with this hash, went from this host to this one at this time".

Finally, when you have the conversation that matters, save it on its own. With a display filter applied, choose File, then Export Specified Packets, select All packets: Displayed, and write a new .pcapng. Hash the new file and note the filter you used to produce it. You now have a small capture you can attach to a report, hand to a classmate, or open in another tool, and a line in your notes that lets anyone reproduce it from the original.

Reading DNS and HTTP at a glance

Two protocols carry most of the story in a beginner's capture, and both read well in the packet list once you know which columns to watch.

DNS. Filter dns. Each query and its response appear as a pair; the Info column shows the name asked for and, on the response line, the address returned. Filter dns.flags.response == 0 to see only the questions, which is a compact list of every name the host tried to resolve, in order. A name you do not recognize, followed a second later by a TCP connection to the address it returned, is the thread to pull. The beaconing post picks it up from there.

HTTP. Filter http.request to see only requests: method, host and path, one per line. Add http.host and http.user_agent as columns (right-click the field, Apply as Column) and the list becomes a browsing history with the client software attached. http.response.code on the responses tells you what the server said. Most web traffic today is TLS and will not decode; filter tls.handshake.type == 1 and read the Server Name field to see which hosts were contacted even when the content is opaque.

That is the whole first hour: fix the clock, write display filters, read Conversations before packets, follow the stream, export the objects, learn the DNS and HTTP columns, save the subset.
