Reading an iPhone sms.db: the iMessage joins and the Cocoa-time trap

An iPhone keeps its messages in a single SQLite file. Getting a readable thread out of it means joining four tables correctly and decoding a timestamp that is neither Unix seconds nor anything most tools guess right the first time.

Mobile forensics is where a lot of students meet their first real database. On an iPhone, the Messages app stores everything in sms.db, a standard SQLite file that lives at /private/var/mobile/Library/SMS/sms.db in a full file-system extraction. Open it in DB Browser for SQLite and you can read every table by hand. That accessibility is exactly why it makes such a good teaching artifact: nothing is locked behind a proprietary parser, so a student has to understand the schema rather than trust a tool's export.

It is also where two specific skills get tested at once. First, a message is not stored in one place: the text, the sender, the conversation and the ordering live in different tables that you have to join. Second, the timestamp is Apple's own epoch, and reading it as Unix time gives an answer that is wrong by thirty-one years. Both are worth teaching deliberately, because both show up on the job and on the mobile certification exams.

The schema, in the order you need it

Four tables carry the conversation, and each answers a different question:

  • message is the body. One row per message, with text, date, is_from_me (1 if the phone's owner sent it, 0 if they received it), service (iMessage or SMS), and a handle_id that points at the other party.
  • handle is the address book of the conversation. Each row is one remote identity, with id holding the phone number in E.164 form or the Apple ID email. message.handle_id joins to handle.ROWID.
  • chat is the thread itself, one row per conversation, with chat_identifier and an optional display_name for group chats.
  • chat_message_join is the bridge. A message does not name its chat directly; this table maps chat_id to message_id, and it is the piece students most often forget.

That last table is the crux. A beginner who selects straight from message gets a flat pile of texts with no sense of which conversation each belongs to, and in a group chat they cannot tell who said what. The join through chat_message_join is what turns the pile back into threads:

SELECT  datetime(m.date/1000000000 + 978307200, 'unixepoch') AS sent_utc,
        CASE m.is_from_me WHEN 1 THEN 'owner' ELSE h.id END   AS sender,
        m.service,
        m.text
FROM        message m
JOIN        chat_message_join cmj ON cmj.message_id = m.ROWID
JOIN        chat c                ON c.ROWID        = cmj.chat_id
LEFT JOIN   handle h              ON h.ROWID        = m.handle_id
WHERE   c.chat_identifier = '+15551234567'
ORDER BY m.date;

The LEFT JOIN on handle matters: an outbound message can have a handle_id of 0, so an inner join quietly drops every message the owner sent. Students who use an inner join here produce a transcript that is missing one side of the conversation, which is a subtle and very teachable mistake.

The Cocoa-time trap

Now the timestamp. On a modern iPhone, message.date is not Unix time. It is Apple's Cocoa Core Data timestamp: the number of nanoseconds since the Mac reference epoch of 2001-01-01 00:00:00 UTC. A single message date looks like 743800000000000000, a number big enough that students assume it is already in milliseconds, or microseconds, and start dividing by guesses.

Read an iPhone message date as Unix seconds and you land in 1970. Read it as Unix nanoseconds and you land tens of thousands of years in the future. The value is right there; the epoch is the whole exam.

The correct decode has two steps. Divide by one billion to get seconds, then add 978307200, the number of seconds between the Unix epoch of 1970 and the Mac epoch of 2001, to shift it onto Unix time. In SQLite that is the datetime(m.date/1000000000 + 978307200, 'unixepoch') expression above. The same transform applies to date_read and date_delivered, which lets a student prove not just when a message was sent but when it was actually read.

There is a historical wrinkle worth mentioning to a class: before iOS 11, message.date was stored in seconds since 2001, not nanoseconds. A student who finds a nine- or ten-digit date rather than an eighteen-digit one is looking at an older device, and the divide-by-a-billion step would push them back to 2001. Teaching the two formats side by side makes the point that a timestamp means nothing without its epoch and its unit.

Putting a name to a number

A phone number is an identifier, not a person. The second database in the extraction, AddressBook.sqlitedb, is where you resolve it: ABPerson holds the contact records and ABMultiValue holds their phone numbers and emails, so joining the handle.id from sms.db against the stored numbers turns +15551234567 into a named contact. That cross-database correlation is the step that converts a raw thread into an investigative finding: this contact, under this saved name, sent this message at this time.

Students who prefer a guided tool can run the same extraction through iLEAPP, which parses sms.db and the address book into an HTML report with the timestamps already decoded. The teachable sequence is to have them answer the question by hand in DB Browser first, then confirm it in iLEAPP, so the automated parser is a check on their reasoning rather than a substitute for it. That is also how a real examiner validates a tool's output before putting it in a report.

A different thread for every student

The iPhone cases in Red Herrings plant a genuine sms.db with the real message, handle, chat and chat_message_join structure, alongside an AddressBook.sqlitedb, so students work the actual schema in the actual tools rather than a flattened export. And because every case is individually seeded, each student's phone has its own contacts, phone numbers, group membership, message text and timestamps. Ask "when did the suspect first message the burner number, in UTC?" and every student has to run their own join and their own Cocoa-time decode to reach their own answer. A copied timestamp is simply the wrong timestamp, because it belongs to someone else's phone.

Every generated variant is re-solved and verified before release by the Fresh Catch check, an independent parser pass that opens the student's own sms.db, performs the joins and decodes the dates, so the answer key is provably correct against the exact database each student receives.
